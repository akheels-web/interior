# PlanSaathi operations

This is a preparation/runbook, not evidence of a public deployment. Use a fresh production database; never promote the seeded local database or `.env.local`.

## Launch sequence

1. Complete the owner decisions in `PRODUCTION-PLAN.md`. Purchase the chosen domain only after reviewing availability and renewal price. Provision a supported Linux VPS; patch the OS, use SSH keys, restrict SSH, and allow public 80/443 only. Keep database/Redis ports private.
2. Copy `deploy/production.env.example` to ignored `.env.production` and `deploy/backup.env.example` to ignored `.env.backup`; restrict both to owner read/write. Generate distinct random secrets. `BETTER_AUTH_SECRET` and `OPS_TOKEN` need at least 48 random characters. The backup encryption key is 32 random bytes encoded as base64; retain a recovery copy outside the server.
3. Create separate R2 Standard application and backup buckets. Disable public `r2.dev` and custom-domain access. Scope each token to its own bucket; the app must not have backup credentials. Do not enable a public asset URL. Apply a seven-day expiration lifecycle to the backup bucket after confirming retention; retain current referenced plan images regardless of project age/archive state.
4. Verify SMTP sender DNS (SPF/DKIM/DMARC) and actual inbox/spam delivery. Configure the exact HTTPS origin in both URL fields, without trailing path/query. Configure Razorpay test keys and an interval-1 monthly INR149900 plan. The signed webhook is `https://<domain>/api/billing/webhook`.
5. Build the app/migration images off-server: `docker build --target app -t plansaathi-app:0.4.0 .` and `docker build --target migrate -t plansaathi-migrate:0.4.0 .`. Also build the patched vendor derivatives: `docker build -t plansaathi-db:0.4.0 deploy/postgres` and `docker build -t plansaathi-proxy:0.4.0 deploy/proxy`. The proxy is standard Caddy 2.11.7 with locked patched Go/network/JOSE dependencies; the runtime images apply available Alpine fixes. Transfer through a private registry or a protected image archive, record final artifact digests and deploy those exact artifacts. Do not include `.env*`, `.local`, private backups or plan uploads in image contexts. Review package/image audits and every open item in `SECURITY-REGISTER.md` before rollout. A base digest alone does not pin packages downloaded during an Alpine update; the final built image is the reviewed deployment artifact.
6. On the server run Compose with `--env-file .env.production -f compose.production.yml`. Start `db`, run `--profile tools run --rm migrate`, then start `app worker caddy`. The app image runs as uid1001; the database has no published port. Create `.private-backups` owned by uid1001 with restrictive permissions before a backup job. Never mount the Docker socket into the app.
7. Register/verify the approved owner email, enable an authenticator in Profile & security and save recovery codes separately. Admin permission requires an explicitly MFA-verified session, not merely an enabled factor. A fresh sign-in may be needed after setup/rotation.
8. Run `npm run launch:check` in a controlled environment with `.env.production` available (the migrate/build image includes its TypeScript runtime). This static configuration check is only one gate. Complete real-provider and load/restore tests below before enabling sales/indexing.

The included Caddyfile expects **DNS-only Cloudflare records** initially and overwrites `X-Real-IP` from its direct peer. Its administration API is disabled; apply reviewed configuration through a controlled container restart. Do not enable an upstream proxy while trusting arbitrary forwarded headers. If enabling the Cloudflare proxy later, configure/maintain verified trusted proxy ranges and client-IP handling in Caddy first, then retest throttling and TLS. Never blindly trust client-supplied `X-Forwarded-For`.

## Health and monitoring

`GET /api/health` returns only `{ok:true|false}` and HTTP200/503. It coalesces/caches probes for five seconds and checks database-backed worker health, unresolved payment jobs and production configuration. Use an external uptime checker after HTTPS exists; alert the founder on failure. No remote monitor was created here.

Internal `/api/ops/tick` and `/api/ops/ready` require the long `OPS_TOKEN`. Caddy blocks those paths publicly. The worker calls the app over the private container network every ten seconds. The super-admin Billing operations panel shows pending/review counts, unconfirmed checkouts, provider-check failures and the last heartbeat. Review this daily. Authentication/R2 resource caps and container log rotation bound common cost/storage failure modes; they do not replace monitoring or DDoS protection.

## Payment safety and recovery

Enable captured payment, subscription charge/status and processed refund webhooks. Raw bytes are HMAC-verified before a minimal event record is committed; customer contact/payment-instrument fields are discarded. Provider fetches happen after durable acceptance. The worker leases jobs, retries with backoff and moves repeated failures to `review` after 12 attempts. A crashed lease becomes claimable after ten minutes. Database transactions/deduplication protect credits from callback/webhook/poll overlap.

One owned checkout is polled per worker tick, no more than once per fifteen minutes. Subscription polling covers invoices created in the recent 35-day window; ready add-on orders are checked for captured/refunded payments. Polls enqueue references for the same independent reconciliation. Polling deduplicates each payment per UTC day; a refund with a missing webhook may therefore wait until the next daily check. This is bounded recent-delivery recovery, not an unlimited historical audit. After a longer outage, compare the provider dashboard against the ledger and request/replay the specific provider events.

An ambiguous order/subscription creation remains `creating`; never mark it failed merely because the HTTP request timed out. Locate its receipt/checkout-intent reference in the correct Razorpay account, verify identity/amount/plan and attach the existing provider reference before retrying reconciliation. An unpaid subscription is reused/blocked regardless of age. A closed/expired provider checkout may need a support review before it can be replaced. Never create a second monthly subscription to work around an unknown first one.

For a `review` event, investigate the stored code, provider payment/invoice/order, ownership and amount first. A controlled operator may reset that exact inbox row to `pending`, attempts0, `available_at=now()` only after resolving the underlying issue; record the reason in the incident log. Replaying a verified event is safe; manually fabricating paid periods/payment rows is not. Administrative compensation credits are a separately audited action and do not represent a payment.

`RAZORPAY_LIVE_APPROVED=false` or `LAUNCH_POLICIES_APPROVED=false` blocks **new** live-mode purchases. Existing signed payments/refunds and polling continue with valid provider credentials. This switch does not cancel existing provider mandates. Use the explicit at-period-end cancellation workflow to stop renewal. Keep test and live plans/secrets separate.

Provider acceptance matrix: verified initial invoice (authorization alone grants nothing), renewal, failed/late payment, browser closed after payment, duplicate and out-of-order delivery, provider timeout, add-on replay, full/partial refund, cancellation and re-subscription. Confirm captured amounts and actual billing timestamps, verify no double credit/charge, and verify cross-account callback denial. These still require real Razorpay test-mode credentials.

## Plan storage

Original PDF/image bytes remain local in the importer. A selected reduced raster preview is validated/re-encoded and stored privately with an owned project reference; geometry stays in PostgreSQL. Existing inline previews migrate on save. The server never accepts a client-selected bucket key. An unchanged preview is omitted from ordinary autosave requests and is retained only against the same owned revision and matching reference metadata. Explicit conflict overwrite sends the full local preview.

Limits include 4M decoded preview pixels, 2,000 pixels per side, 4MB output, two concurrent decodes, 20 new preview uploads/account/hour, 2,000 new uploads/app/day and the configured total storage budget. The browser normally saves a 1,600-pixel reference. R2 outage, quota exhaustion or a failed CAS preserves the previous saved pointer and the in-memory draft. Unreferenced replacements/failed uploads are collectible after seven days; archived project previews are retained. No server-side version-history product is promised.

## Backups and restore

`deploy/backup.sh` streams a PostgreSQL custom-format dump directly into AES-256-GCM encryption, then uploads only the encrypted envelope to the separate private backup bucket. No plaintext dump is written during backup. A pipeline failure stops upload. The envelope has a random IV and authentication tag, refuses overwriting outputs and caps a dump at 250MiB. Keep the encryption key outside both app containers and the backup bucket; losing it makes backups unusable.

After a manual successful backup/restore, install the supplied systemd service/timer in the actual deployment path, review its daily UTC time, then enable it. Monitor failed jobs and backup age/size. Configure backup-bucket expiration and local encrypted-file retention explicitly; the script does not silently delete existing recovery copies. Include protected copies of server environment/configuration and a recovery inventory of R2 assets as part of operations. A database dump alone does not copy the plan objects.

Restore into a new isolated database first. Download the encrypted file privately, run `node scripts/backup.mjs decrypt <encrypted-file> <new-plaintext-output>`, then `pg_restore --exit-on-error --no-owner` into the disposable database. Authenticate/decrypt completely before restoring; a wrong key or tampered ciphertext never produces a completed plaintext output. Verify row counts, owner isolation, stored object references and a sample login/project. Remove the temporary plaintext securely according to the host's storage policy. Never restore over a production database without a reviewed recovery plan and current backup.

A local real PostgreSQL dump → encryption → authenticated decryption → disposable restore → sentinel check passed on 30 October 2026. Cloud backup upload and selected-host restore remain unverified until configured. Do not blindly rotate `BETTER_AUTH_SECRET`: it also protects encrypted authenticator secrets. Use the auth provider's supported rotation/migration procedure and a rehearsed recovery path.

## Patching and rollback

Vendor bases are pinned to digests verified on 30 October 2026; built derivatives include available distribution patches. CI pins official GitHub actions and runs install/audit/typecheck/tests/build, all three runtime image builds and an image-scan gate for fixable medium/high/critical advisories. It runs on pushes, pull requests, manual requests and weekly. Dependabot checks npm, Docker, Go modules and Actions weekly. Unfixed findings are not automatically accepted: keep them in `SECURITY-REGISTER.md` and review their reachability before launch. These workflows become active only when this repository is put on GitHub. No repository/PR was published here. Recheck Node LTS, dependencies and image CVEs before deployment and after advisories; apply tested updates promptly. Build with fresh distribution layers (`--no-cache` for release patch refreshes), then re-scan and retest the resulting artifacts.

Before an update: take an encrypted backup, test migration/rollback against a disposable restore, build immutable images and retain the previous image/config. SQL migrations are forward-only; an old image may not understand a new schema. Prefer a forward fix or an explicitly rehearsed database recovery rather than blindly switching an old container onto changed data. Do not copy old `.env.local` over authoritative server secrets.

Capacity gate: test the selected VPS with ten concurrent representative accounts, repeated saves, imports and 30-room/300-object projects. Measure p95 API latency, dropped frames on target customer laptops, memory, DB connections and storage/queue growth. Local correctness tests and browser screenshots do not establish production capacity or guarantee zero lag.
