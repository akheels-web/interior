Server configuration

- PostgreSQL is authoritative for accounts, Better Auth sessions, projects, creation-credit usage, checkout intents, paid periods and payment idempotency. Run `migrations/runner.ts` with the installed TypeScript runner and the intended environment loaded before starting the app. The runner applies Better Auth's official generated schema, then the versioned platform SQL.
- `DATABASE_URL` is required. Local Docker uses loopback without TLS. For a remote database set `DATABASE_SSL=require`; certificate verification remains enabled. Set `DATABASE_SSL_CA` to a PEM CA chain if the server uses a private CA (`\\n` escapes are accepted). Do not use `NODE_TLS_REJECT_UNAUTHORIZED=0` or disable certificate validation.
- `BETTER_AUTH_URL` is the exact trusted application origin; `BETTER_AUTH_SECRET` must be a random secret of at least 48 random characters. Set `SUPER_ADMIN_EMAIL` explicitly for production. Only development defaults to the owner's approved bootstrap address. Bootstrap promotion occurs only after the configured address signs in with a verified email. Registration inputs cannot assign roles.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, optional `SMTP_SECURE`, `SMTP_USER` and `SMTP_PASS` configure verification and password-reset mail. Local Mailpit uses `127.0.0.1:1028`; delivery UI is `127.0.0.1:8028`. The backend never prints verification links or reset tokens.
- `REDIS_URL` is optional. Redis caches request-rate counters; a failure falls back to SQL. Better Auth's login/reset throttling remains database backed. Redis is never the sole store for sessions, quota or subscription state.
- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_PLAN_ID`, and `RAZORPAY_WEBHOOK_SECRET` are all required to enable checkout. The configured plan must be monthly, interval 1, INR 149900 paise. The signed raw-body webhook endpoint is `/api/billing/webhook`. Provider callbacks are reconciled against server-fetched captured payment, order/invoice and subscription/plan data. `subscription.authenticated`/`activated` do not grant credits.
- Without payment credentials, normal new accounts have no paid period and cannot create projects. There is no admin quota bypass. Explicit development fixtures must remain separate from production routes and be labeled as offline fixtures.
- The optional `seedDevelopmentEntitlement(email)` helper requires `NODE_ENV=development`, `ALLOW_OFFLINE_BILLING_FIXTURES=true`, a loopback database and an already verified email. It creates an idempotent, audited offline period for the current month. The API reports `offline_development_fixture`; no real payment is claimed. Migration 002 stores provenance, and production quota/checkout logic excludes all development/integration periods even if someone copies a local database into production.
- Integration tests require `TEST_DATABASE_URL` pointing to the dedicated `forma_test` database. They create isolated synthetic accounts and billing facts, never contact Razorpay or make real charges. Real-provider test-mode validation remains necessary once credentials exist.

See ../../PRODUCTION-PLAN.md and ../../OPERATIONS.md for private R2, worker/health, MFA session assurance, production gates, encrypted backup and provider-recovery configuration. Original plan bytes remain local; reduced previews are private objects, not public URLs.
